# 公开披露案例写作蓝图

## 暂定题目

**《甲软件和信息技术服务企业税收风险管控案例——基于两期公开年报与官方政策的可复现观察》**

这里的“甲企业”对应已核验的公开披露样本；对外匿名写作不得改变任何源数据、来源或期间。正式作品应说明资料来自公开披露，不表述为企业内部调研资料。

## 叙事主线

以“项目/订阅类服务的履约与回款、研发投入、政府补助、合同凭证管理”为业务线索：先用公开财务披露形成纵向观察，再用政策确定需要核验的税务事实，最后把无法从年报得到的资料列为证据缺口。案例的价值是建立可复算的筛查与证据补强路径，而非从年报直接认定违法。

## 正文结构

1. **案例边界与资料真实性**：说明公开资料路线、报告期间、文件哈希和匿名规则；引用 `yonyou_annual_report_verification.csv`。
2. **企业与业务理解**：仅依据年报中披露的主营业务、收入模式和公开说明写作；无法确认的业务事实标记 `TODO_MISSING_DATA`。
3. **数据治理与可复现性**：说明原始年报、文本提取、字段血缘和运行命令；核心数字只引用 `outputs/tables/` 的代码输出。
4. **指标筛查**：按“收入/回款与合同资产负债、研发、政府补助、税费综合观察、合同凭证完整性、关联交易资料完整性”逐项展示 `OBSERVATION`，不设置主观阈值。
5. **政策核验**：逐条引用 `sources/policies/index.csv`；把税率、优惠资格和业务适用性未核实部分写为 `POLICY_UNVERIFIED` 或 `NEED_TAX_REVIEW`。
6. **假阳性排除与证据补强**：每项观察必须说明可能的正常商业解释，以及需要何种合同、发票、申报或台账排除。
7. **结论**：仅总结公开资料下的观察和待核事项；禁止写“少缴税”“虚开”“违法”或任何 `CONFIRMED_RISK`。
8. **整改与长效监控建议**：使用条件式建议，例如“如后续核验发现研发辅助账与申报不一致，则应……”，不可假设已存在违规。

## 观察—证据—结论的固定格式

每一个指标都按下列顺序写作：

`公开字段和来源 -> 代码公式 -> 两期观察 -> 正常业务解释 -> 所需补充证据 -> 政策核验 -> 结论上限`

“结论上限”在当前资料条件下统一为 `OBSERVATION`；不得因指标变化直接升级为 `ANOMALY` 或 `POTENTIAL_RISK`。

## 答辩材料必须准备的文件

- 年报哈希核验表：`docs/research/yonyou_annual_report_verification.csv`；
- 字段可得性及血缘：`docs/research/yonyou_public_field_availability.csv` 和 `outputs/tables/yonyou_public_financial_fields.csv`；
- 指标观察和候选覆盖：`outputs/tables/yonyou_public_indicator_observations.csv` 与 `docs/research/yonyou_public_indicator_coverage.csv`；
- 政策索引、原始网页和提取文本：`sources/policies/`；
- Workflow 日志与 Gate：`docs/workflow/`。

## 明确禁止

- 不用虚构企业、虚构合同、虚构发票、虚构申报表或虚构访谈补足证据；
- 不把合成测试夹具混入案例分析；
- 不手改数字、比例、图表或结论；
- 不把缺失证据写成“已核实”。
